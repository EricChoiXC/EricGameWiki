# 业务流转公共规范

> 本文档为 `EricGameWiki` 项目的后端业务流转规范
> 本规范覆盖 `web` 和 `admin` 系统的后端系统流转
> 各后端模块（`sys` / `wiki` 等）的业务逻辑文档应引用本文档，并在正文中声明"通用流转规范遵循本文档，不再重复编写"。
> 涉及非通用（模块特有）的流转约定，各模块文档仍需要自行编写。

## 2. 后端包结构

> 本节为 `AGENTS.md` 第 1 节"仓库结构"与第 4 节"后端开发约束"在业务流转层面的细化，冲突以 `AGENTS.md` 为准。

### 2.1 根包与模块包

- 后端统一根包路径：`com.wiki.web` / `com.wiki.admin`，分别对应 `web` 系统与 `admin` 系统
- 如后端用户模块归入 `com.wiki.admin.org` 根包
- WIKI 模块归入 `com.wiki.web.wiki` 和 `com.wiki.admin.wiki` 根包
- 跨系统复用的公共逻辑、基类、工具类等公共代码统一归入 `com.wiki.common` 包

### 2.2 模块内分层包结构

每个模块必须按以下包结构组织，禁止跨层混放：

```text
com.wiki.{系统}.{模块}
├─ controller           # 接口入口，仅做参数校验与响应
├─ service              # 业务逻辑承载层
│  ├─ impl              # 默认实现
│  ├─ listener          # 事件监听器（领域事件消费者）
│  ├─ webservice        # 远程 SOAP/内部 RPC 服务调用入口
│  └─ task              # 定时任务入口
├─ dao                  # 数据访问层
│  └─ impl              # 默认实现
├─ model                # 数据模型
│  ├─ request           # *Request.java 请求对象
│  ├─ response          # *Response.java 响应对象
│  ├─ dto               # *Dto.java / *Do.java 视图与领域对象
│  └─ mapper            # MyBatis Mapper 接口与转换 Mapper
├─ util                 # 工具类（仅放可复用通用逻辑）
├─ properties          # 配置属性绑定类
└─ resolver            # 接口级鉴权 Resolver
```

### 2.3 分层职责（流转契约）

| 层 | 允许调用 | 禁止调用 | 流转说明 |
|----|----------|----------|----------|
| `Controller` | `CRPService` / 参数校验 / 响应封装 | Dao / Mapper / 直接 DB / 其他模块 Service | 仅做请求接入与响应封装，不承载业务 |
| `CRPService` | 自身模块 `IService` / 其他模块 `IService` / `WebService` 入口 / `RestService` 入口 | Dao / Mapper / 直接 DB | 模块间调用入口与跨模块参数校验，不承载业务逻辑 |
| `IService` / `ServiceImpl` | 自身模块 `IDao` / 事件发布 / `Util` / 同模块子 Service | 其他模块 `IDao` / `Controller` | 承载业务逻辑，复杂流程必须拆分子方法 |
| `WebService` / `RestService` | 外部系统接口 / 远程 RPC 入口 | 业务逻辑 / Dao | 外部系统调用入口与参数校验，不承载业务逻辑 |
| `IDao` / `DaoImpl` | 对应的 `Mapper` | 业务逻辑 / 跨表 Join 业务规则 | 与 Mapper 一对一对接，不写业务 |
| `Util` | 纯函数工具 | 任何业务层 / DB | 可复用小型通用逻辑，禁止业务堆积 |
| `Resolver` | 鉴权所需的只读 Service / Dao | 业务写操作 | 接口级鉴权，明确返回允许/拒绝结论 |
| `Listener` | 处理事件 / 调用 `IService` | `Controller` / 直接返回 HTTP 响应 | 领域事件异步消费 |
| `Task` | 调用 `IService` / `CRPService` | `Controller` / 直接返回 HTTP 响应 | 定时调度入口 |

### 2.4 包间调用方向约束

- 调用方向严格自上而下：`Controller → CRPService → IService → IDao → Mapper`
- **禁止反向调用**：`Dao` / `Mapper` 不得调用 `Service`；`Service` 不得调用 `Controller`
- **禁止跨模块直连 Dao**：模块 A 的 `IService` 调用模块 B 的 `IService`，禁止直接调用模块 B 的 `IDao`
- **禁止 Controller 跨模块调用**：跨模块调用必须经 `CRPService` 转发
- 同模块内 `ServiceImpl` 可拆分子 Service，但子 Service 不得反向调用父 Service（禁止循环依赖）

### 2.5 命名与文件落位约束

| 类型 | 命名规则 | 落位目录 |
|------|----------|----------|
| Controller | `{业务名}Controller` | `controller/` |
| CRPService | `I{业务名}CRPService` / `{业务名}CRPServiceImpl` | `service/` |
| Service | `I{业务名}Service` / `{业务名}ServiceImpl` | `service/` + `service/impl/` |
| WebService | `I{业务名}WebService` / `{业务名}WebServiceImpl` | `service/webservice/` |
| RestService | `I{业务名}RestService` / `{业务名}RestServiceImpl` | `service/webservice/` |
| Dao | `I{业务名}Dao` / `{业务名}DaoImpl` | `dao/` + `dao/impl/` |
| Mapper | `{业务名}Mapper` | `model/mapper/` |
| Request | `{业务名}{动作}Request` | `model/requests/` |
| Response | `{业务名}{动作}Response` | `model/response/` |
| Dto / Do | `{业务名}Dto` / `{业务名}Do` | `model/dto/` |
| Resolver | `{业务名}{动作名}Resolver` | `resolver/` |
| Listener | `{业务名}{事件名}Listener` | `service/listener/` |
| Task | `{业务名}Task` | `service/task/` |

> 与 `AGENTS.md` 第 7.1 节后端命名冲突时，以 `AGENTS.md` 为准；本表仅补充流转相关命名。

### 2.6 资源文件结构

模块资源文件按以下结构组织（与 `yml配置文件内容规范.md` 保持一致）：

```text
resources/
└─ ${模块}/
   ├─ mappers/
   │  ├─ {业务名}Mapper.xml
   │  └─ ...
   ├─ application.yml       # 模块信息配置
   ├─ roles.yml            # 权限信息配置
   ├─ dict.yml             # 字典码值配置
   ├─ process.yml          # 流程信息配置
   └─ *.yml                # 其他配置文件
```

- 无模块归属的公共配置统一放在 `resources/common/` 下
- 跨模块共享的 MyBatis resultMap / sql 片段统一放在 `resources/common/mappers/` 下

## 3. 前端接口调用规范

> 本节为前端调用后端接口的流转约束，接口报文格式以 [接口公共规范.md](接口公共规范.md) 为准，本节不重复约定报文字段。

### 3.1 调用前缀与基础路径

- 前端 Axios `baseURL` 统一配置为 `/api/v1/{系统}`，仅 API 请求走该前缀
- 前端页面通过裸根路径 `/` 直接访问，禁止将页面路径混入 API 前缀
- 后端 Controller 的 `@RequestMapping` 必须显式包含完整路径前缀（如 `@RequestMapping("/api/v1/sys/org/user")`）
- **禁止**使用 `server.servlet.context-path` 在全局层面对静态资源和 API 做统一前缀

### 3.2 调用方向约束

| 调用场景 | 允许 | 禁止 |
|----------|------|------|
| 页面组件 | 调用 `api/` 模块封装的请求函数 | 直接在组件内 `axios.*` 散落请求 |
| Pinia store | 调用 `api/` 模块封装的请求函数 | 直接调用底层 axios 实例 |
| `api/` 模块 | 调用统一 axios 实例 | 调用其他 `api/` 模块（避免循环依赖） |
| 工具函数 | 纯函数工具 | 调用 `api/` 模块或 store |

### 3.3 API 封装约定

- `api/` 目录按模块拆分，文件名采用小写或 `kebab-case`（如 `system.js`、`wiki-project.js`）
- 每个 `api/` 文件只负责一个模块的接口封装，禁止跨模块混编
- 接口函数命名采用可读性优先的英文语义命名，建议 `{动词}{资源}`（如 `loadWikiProject`、`saveWikiProject`）
- 所有请求必须经过统一 axios 实例，由实例统一处理：
  - 请求头注入（如 `Authorization: Bearer <token>`）
  - 响应统一解包（如 `success` / `code` / `data` / `list` / `query` 字段）
  - 错误码统一路由（如 401 跳登录、403 提示无权限）
- 禁止在 `api/` 模块内写业务逻辑，仅做请求构造与响应返回

### 3.4 调用鉴权流转

- 前端按钮显隐可基于批量鉴权接口做预判断
- 批量鉴权接口仅用于 UI 预判，**不能替代后端最终鉴权**
- 后端每个接口的 `Resolver` 必须在 Controller 或 Service 执行核心逻辑前完成鉴权
- 鉴权核心参数必须是"接口 + 文档 ID"，所有单据访问、编辑、删除、提交流程必须传入文档 ID

### 3.5 调用流程约定

#### 3.5.1 查询类调用

- 单 `id` 传参或无参查询使用 `GET`
- 包含非 `id` 查询条件使用 `POST` `/list`
- 分页参数统一使用 `pageNum`（从 1 开始）、`pageSize`，响应统一使用 `total`、`pages`、`records`
- 关键词模糊搜索统一使用 `keyword` 字段
- 查询条件构造遵循 [查询标准.md](查询标准.md)

#### 3.5.2 写操作调用

- `/save`：`POST`，返回新创建记录的 `field_id`
- `/update`：`PATCH`，支持部分字段更新，**禁止使用 `PUT`**
- `/delete?fieldId=${id}`：`DELETE`，物理删除或逻辑删除由具体接口决定
- `/import`：`POST`，批量导入
- `/export`：`POST`，批量导出
- `/download?fieldId=${id}`：`GET`，单据下载

#### 3.5.3 初始化与加载

- `/init`：`GET`，页面初始化数据加载
- `/load?fieldId=${id}`：`GET`，单据详情加载

### 3.6 通用请求 / 响应报文流转

报文格式遵循 [接口公共规范.md](接口公共规范.md) 第 3.5、3.6 节，本节不重复约定字段。流转约束如下：

- 前端构造请求时，`data` 对象优先仅传入数据库表有的字段
- 后端响应 `data` 对象优先仅返回数据库表有的字段，敏感字段（如密码、Token）必须剥离
- 分页信息统一通过 `query` 字段流转，禁止与业务数据混入同一对象
- 除上述内容以外的其他参数统一通过 `map` 字段流转，禁止占用 `data` / `query` 的字段名

### 3.7 异常与错误码流转

| 错误码 | HTTP 状态码 | 前端处理建议 |
|--------|-------------|--------------|
| SUCCESS | 200 | 正常处理 |
| BAD_REQUEST | 400 | 表单校验回填错误信息 |
| UNAUTHORIZED | 401 | 清除登录态，跳转登录页 |
| FORBIDDEN | 403 | 提示无权限，禁用对应按钮 |
| NOT_FOUND | 404 | 提示资源不存在 |
| CONFLICT | 409 | 提示数据冲突，引导用户修改 |
| INTERNAL_ERROR | 500 | 提示系统异常，记录日志 |

- 前端统一在 axios 响应拦截器中处理错误码路由，禁止在 `api/` 模块或页面组件内重复实现
- 后端抛出业务异常必须携带可追踪原因或权限码，由 `Controller` 统一封装为标准响应报文

### 3.8 跨系统调用约定

- 双系统部署下，管理员系统（`admin`）与访客系统（`web`）各自独立部署
- 前端不得跨系统直接调用对方 API，跨系统数据流转必须经后端服务间调用（见第 4 节）
- 禁止 `web` 系统通过专属接口只读访问 `admin` 系统的字典 / 组织架构数据

## 4. 后端内部调用其他服务规范

### 4.1 调用方向总则

后端内部调用遵循以下方向约束，禁止逆向或跨层调用：

```text
Controller
   ↓
CRPService ──────→ 其他模块 CRPService / IService
   ↓                        ↓
IService ──────→ 其他模块 IService（经 CRPService 转发优先）
   ↓
IDao → Mapper → DB
```

- 模块内调用：`Controller → CRPService → IService → IDao`
- 跨模块调用：必须经 `CRPService` 转发，禁止 `Controller` 直连其他模块 `IService`
- 跨系统调用（`web` ↔ `admin`）：必须经 `WebService` / `RestService`，禁止直接 `import` 对方系统的 `IService`
- 外部系统调用：必须经 `WebService` / `RestService`，统一在 `service/webservice/` 下封装

### 4.2 跨模块调用约束

| 调用方 | 允许调用目标 | 禁止调用目标 |
|--------|--------------|--------------|
| 模块 A `CRPService` | 模块 B `CRPService` / `IService` | 模块 B `IDao` / `Mapper` |
| 模块 A `IService` | 模块 B `IService`（需经 A 的 `CRPService` 转发优先） | 模块 B `IDao` / `Mapper` |
| 模块 A `Listener` | 模块 B `IService`（消费模块 B 发布的事件） | 模块 B `IDao` |
| 模块 A `Task` | 模块 A `CRPService` / `IService` | 模块 B `IService`（如需跨模块，需经自身 `CRPService` 转发） |

- 跨模块调用参数禁止直接传递 `Do` 对象，必须转换为 `Dto` 或 `Request` 对象
- 跨模块调用的异常由调用方 `CRPService` 统一捕获并封装为业务异常
- 是：跨模块调用是否需要统一的事务传播策略（默认 `REQUIRED`，禁止跨模块 `REQUIRES_NEW`）

### 4.3 事件驱动流转

- 领域事件统一通过 Spring `ApplicationEventPublisher` 发布
- 事件对象必须放在 `model/dto/` 下，命名 `{业务名}{动作}Event`（如 `WikiProjectApprovedEvent`）
- 事件监听器放在 `service/listener/` 下，命名 `{业务名}{事件名}Listener`
- 事件发布必须由 `IService` 完成，禁止 `Controller` / `Dao` 直接发布事件
- 监听器只能消费事件并调用 `IService`，禁止反向调用 `Controller` 或直接返回 HTTP 响应
- 是：事件是否支持异步（`@Async`），默认同步；异步事件需明确声明并保证幂等

### 4.4 定时任务流转

- 定时任务统一放在 `service/task/` 下，命名 `{业务名}Task`
- 定时任务只能作为调度入口，业务逻辑必须委托给 `IService` / `CRPService`
- 定时任务禁止直接调用 `Dao` / `Mapper`，禁止承载业务逻辑
- 定时任务的调度配置统一在模块 `application.yml` 中管理

### 4.5 外部系统调用约束

- 外部系统调用（HTTP / SOAP / RPC）统一经 `WebService` / `RestService`，放在 `service/webservice/` 下
- `WebService` / `RestService` 只负责调用入口与参数校验，不承载业务逻辑
- 外部系统调用的配置（URL / 超时 / 重试）统一在模块 `application.yml` 中管理，禁止硬编码
- 外部系统调用的异常必须转换为业务异常，由调用方 `IService` 统一处理
- 否：是否引入统一的外部调用熔断 / 限流组件（如 Resilience4j）
- 是：外部系统调用的统一日志记录策略（请求 / 响应 / 耗时 / 错误码）

### 4.6 鉴权流转

- 接口级鉴权统一由 `Resolver` 完成，放在 `resolver/` 下
- `Resolver` 至少接收：当前用户、接口标识、文档 ID
- `Resolver` 必须明确返回允许/拒绝结论，并给出可追踪原因或权限码
- `Controller` 或 `CRPService` 在执行核心逻辑前必须先完成鉴权
- 批量鉴权接口只用于权限预判，**不能替代目标接口最终鉴权**
- 跨模块调用的鉴权由调用方 `CRPService` 委托目标模块 `Resolver` 完成，禁止跳过鉴权

### 4.7 审计流转

- 写操作（增/删/改）统一记录审计日志
- 审计日志的写入由 `sys.audit` 模块统一承载，其他模块通过事件或 `CRPService` 调用
- 是：审计日志的同步 / 异步策略（默认异步，写操作不阻塞主流程）
- 是：审计日志的字段范围（操作人、操作时间、接口标识、文档 ID、操作前后快照）

### 4.8 异常流转

- 业务异常统一继承自基础业务异常类
- 业务异常必须携带：错误码、可追踪原因、可选的权限码
- `Dao` / `Mapper` 抛出的数据访问异常由 `IService` 统一捕获并转换为业务异常
- 跨模块调用异常由调用方 `CRPService` 统一捕获并封装
- `Controller` 统一通过全局异常处理器将业务异常封装为标准响应报文（遵循 [接口公共规范.md](接口公共规范.md) 3.7 错误码约定）
- 禁止在 `Dao` / `Mapper` / `Util` 中处理异常并返回默认值，必须向上抛出

### 4.9 事务流转

- 事务边界统一在 `IService` 层通过 `@Transactional` 声明
- 禁止在 `Controller` / `Dao` / `Mapper` / `Util` 上声明事务
- 跨模块调用的事务传播策略：TBD（默认 `REQUIRED`，禁止跨模块 `REQUIRES_NEW` 防止事务悬挂）
- 不引入：是否引入分布式事务（如 Seata），默认不引入，跨系统调用优先采用最终一致性 + 事件驱动

### 4.10 调用链路追踪

- 不引入：是否引入统一链路追踪（如 SkyWalking / OpenTelemetry）
- 是：跨模块调用的 traceId 透传策略（默认通过 MDC 透传）
- 是：外部系统调用的 traceId 透传策略（默认通过 HTTP Header 透传）

## 5. 编码规则补充

- 所有文件均使用 UTF-8 编码
- 不允许在 `Controller`、`Dao` 中编写业务逻辑
- 复杂业务流程必须在 `Service` 中拆分为可读的子方法
- 公共逻辑优先复用，禁止复制粘贴形成多份实现
- 跨模块调用必须经 `CRPService` 转发，禁止跨模块直连 `Dao`
- 同一业务规则只能有一份实现，禁止在多个 `Service` 中重复实现
- 不同后缀且不同功能的类文件应分开存放在不同子目录中（如 `*Request.java` 放 `requests/`，`*Vo.java` 放 `dto/`），禁止混放
- 后端内部调用禁止使用 `static` 方法承载业务逻辑，禁止通过 `static` 绕过分层
